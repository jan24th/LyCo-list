# 实现 Assign 事务与幂等分配通知

## 用户故事

作为用户，我希望将任务分配给其他人并生成确定性通知，以便分配可靠且不会重复。

## 范围

### 包含
- 实现任务 assignee 的更新
- 使用事务保证任务分配更新与通知创建的原子性
- 基于确定性规则生成通知 ID，保证重试幂等
- 事务失败时回滚，不创建通知

### 不包含
- 任务与提醒的基础 CRUD
- 任务移动、完成、恢复
- 通知的实际投递渠道（如推送、邮件）

## 验收标准

### 场景 1：将任务分配给用户

Given 一个已存在的任务
When 用户将任务分配给另一个用户
Then 任务 assignee 被更新

### 场景 2：确定性通知 ID

Given 分配操作被重试
When 事务再次执行
Then 通知 ID 是确定性的，不会创建重复通知

### 场景 3：失败时回滚事务

Given 分配更新失败
When 事务执行
Then 不会创建通知

### 2026-07-27 Triage: ready-for-agent

阻塞已解除：`01`（可选 assignee 查询）和 `02`（任务 CRUD）均已 resolved。当前 `PATCH /api/tasks/{id}` 已接受 `assigneeIds`，但 `createTask` / `updateTask` 仍使用单次 `PutCommand`，SST task handler 也尚未授权 `dynamodb:TransactWriteItems`。本票正是补齐这些缺口；无需新增路由。

裁定：

1. **覆盖创建与更新**：`POST /api/tasks` 带非空 `assigneeIds` 时，也必须把创建任务与通知写入同一个事务。设计明确允许创建时选择 assignee，且对 `assigneeIds` 的新增都要求创建通知。空 assignee 的创建保持现有单次条件 `PutCommand`。
2. **新增集语义**：PATCH 仅为相对现有 `assigneeIds` 新增的接收人创建通知；移除、重排或原集合不变时不创建通知。自分配没有设计例外，当前操作者若是新增 assignee 也属于接收人。
3. **输入唯一性**：`assigneeIds` 是集合而非多重列表。共享 task schema 必须拒绝重复 ID，避免同一 DynamoDB 事务写入重复 notification key；既有最多 20 人限制保持不变。
4. **任务与通知事务**：有新增接收人时，以一个 `TransactWriteCommand` 原子写入条件更新后的任务和每位新增接收人的 `NOTIFICATION`。任务项沿用 `version = :expectedVersion AND attribute_not_exists(deletedAt)`；每个通知项以 `attribute_not_exists(PK)` 条件写入。事务成功后返回本地构造的 next task；事务失败不得再发出单独写入。
5. **通知记录契约**：通知使用 `PK=NOTIFICATION#<id>`、`SK=METADATA`、`GSI1PK=USER#<recipientId>#NOTIFICATIONS`、`GSI1SK=NOTIFICATION#<now>`、`entityType=NOTIFICATION`，并写入 `type: "assignment"`、`recipientId`、`taskId`、`taskTitle`、`message`、`isRead: false`、`createdAt` 和 `version: 1`。为使后续标记已读的 `expectedVersion` 可用，同步将 shared `notificationSchema` 纳入 `version` 字段。
6. **确定性 ID**：通知 ID 必须是满足既有 shared schema 的 UUID，使用固定命名空间从 `taskId`、`recipientId` 与**新任务版本号**确定性派生；不得调用 `randomUUID`。同一任务版本对同一接收人重试必须生成相同 ID；接收人被移除后在更高版本重新加入则生成新 ID。
7. **错误与权限**：将条件失败导致的 transaction cancellation 映射为既有 `ConflictError`/HTTP 409；其他失败保留 500。`taskHandler` 增加最小权限 `dynamodb:TransactWriteItems`。不调用 Cognito 验证 assignee 是否存在，不改 notifications Lambda、前端或轮询逻辑。
